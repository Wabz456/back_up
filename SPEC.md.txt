### 0.1 Propósito de esta especificación

Este documento consolida los requisitos funcionales, requisitos de datos,
reglas de negocio, requerimientos SQL, arquitectura, plan de implementación,
plan de pruebas y criterios de aceptación del Proyecto Fase 2.

El documento se construye a partir de:

1. `Caso5_ProyectoFase2.pdf`, enunciado oficial de Fase 2.
2. `InformeFase1_Grupo5a.docx`, informe y modelo propuesto en Fase 1.
3. `RubricaProyectoFase2.pdf`, criterios de evaluación.
4. `DECISIONES_DISENO.md`, derivado del registro de decisiones pendientes.

### 0.2 Prioridad de las fuentes

Cuando exista una diferencia entre documentos, se aplicará el siguiente orden:

1. Enunciado oficial de Fase 2.
2. Observaciones docentes documentadas.
3. Rúbrica de Fase 2.
4. Decisiones formalmente aprobadas por el equipo.
5. Informe de Fase 1.
6. Propuestas aún no aprobadas.

### 0.3 Convenciones

- **Obligatorio:** requisito expreso del enunciado o de la rúbrica.
- **Heredado de Fase 1:** componente propuesto en el informe anterior que debe
  ser revisado antes de considerarse definitivo.
- **Pendiente:** decisión que el equipo aún no ha aprobado formalmente.
- **Requiere aclaración docente:** decisión que no puede cerrarse con certeza
  utilizando solo los antecedentes disponibles.
- **Por definir:** no se debe implementar una alternativa hasta que exista una
  decisión registrada.
- Los nombres de tablas y atributos de este documento son provisionales hasta
  congelar el modelo relacional final.
- Este documento no sustituye el MERE, el modelo de MySQL Workbench ni el
  registro de decisiones.

# 1. Objetivo y alcance

## 1.1 Objetivo general

Corregir y consolidar el modelo de datos desarrollado en Fase 1, implementar
una base de datos relacional en MySQL, poblarla con datos sintéticos coherentes,
resolver doce requerimientos de información mediante seis vistas y seis
procedimientos almacenados, y construir un Producto Mínimo Viable web integrado
con la misma base de datos.

El sistema representa las operaciones de una empresa internacional que
comercializa minerales, fósiles y gemas para coleccionistas, museos y centros
de investigación. También considera colecciones temáticas, exposiciones,
certificaciones de autenticidad, reservas, personal, ventas y evaluaciones.

## 1.2 Objetivos específicos

1. Revisar y corregir las reglas de negocio y el MERE de Fase 1.
2. Construir el modelo relacional definitivo en MySQL Workbench.
3. Implementar tablas, claves y restricciones en MySQL 8.x.
4. Crear un script integral capaz de reconstruir la base de datos desde cero.
5. Generar datos sintéticos suficientes, coherentes y reproducibles.
6. Implementar seis vistas y seis procedimientos almacenados.
7. Construir un PMV en Python y Streamlit.
8. Conectar el PMV a la misma base de datos utilizada por los objetos SQL.
9. Implementar un formulario transaccional de venta.
10. Implementar un CRUD sobre al menos dos tablas básicas o maestras.
11. Implementar inicio de sesión con al menos dos roles reales y permisos
    diferenciados.
12. Implementar un dashboard con cuatro preguntas de negocio.
13. Desplegar la aplicación y la base de datos mediante Docker y Docker Compose.
14. Mantener trazabilidad entre requisitos, modelo, scripts, aplicación,
    pruebas, informe y evidencias.

## 1.3 Alcance incluido

El proyecto incluye:

- corrección del MERE;
- modelo relacional definitivo;
- base de datos MySQL;
- PK, FK, `UNIQUE`, `NOT NULL`, `CHECK` y demás restricciones justificadas;
- datos sintéticos;
- seis vistas;
- seis procedimientos almacenados;
- aplicación web en Streamlit;
- conexión con SQLAlchemy y PyMySQL;
- formulario transaccional de venta;
- CRUD sobre al menos dos tablas;
- autenticación y autorización básica;
- dashboard con cuatro preguntas;
- visualizaciones con Plotly;
- procesamiento de datos con Pandas;
- contenedores Docker para la aplicación y la base de datos;
- matriz de responsabilidades;
- bitácoras individuales;
- evidencias de pruebas y ejecución;
- informe, presentación y defensa.

## 1.4 Fuera de alcance

Salvo que posteriormente se incorpore como requisito formal, no se considera
obligatorio:

- comercio electrónico público;
- pagos electrónicos;
- integración bancaria;
- facturación tributaria;
- envío de correos o notificaciones;
- recuperación automática de contraseña;
- autenticación multifactor;
- auditoría avanzada;
- gestión documental de archivos de certificados;
- integración con servicios externos;
- aplicación móvil;
- analítica predictiva;
- funcionalidades adicionales que sustituyan alguna de las cuatro
  funcionalidades obligatorias del PMV.

La incorporación de funcionalidades adicionales no reemplaza los requisitos
evaluables del proyecto.

## 3.2 Casos de uso obligatorios

### CU-01. Iniciar sesión

**Actor principal:** Usuario no autenticado.

**Precondiciones:**

- existe una cuenta activa;
- la cuenta posee la información necesaria para autenticarse;
- la cuenta tiene asignado al menos un rol si esa regla es aprobada.

**Flujo principal:**

1. El usuario ingresa sus credenciales.
2. El sistema valida los datos contra la base MySQL.
3. El sistema obtiene los roles o permisos asociados.
4. El sistema crea una sesión.
5. El sistema muestra únicamente las funcionalidades autorizadas.

**Flujos alternativos:**

- credenciales inválidas;
- cuenta inexistente;
- cuenta inactiva;
- cuenta sin rol o sin permisos.

**Postcondición:** sesión autenticada con permisos efectivos.

> Pendiente: estructura de credenciales, roles y matriz de permisos.

---

### CU-02. Registrar una venta

**Actor principal:** Usuario con permiso de venta.

**Precondiciones:**

- usuario autenticado y autorizado;
- cliente existente;
- trabajador o gestor comercial existente;
- una o más piezas existentes y elegibles para venta;
- reglas definitivas de disponibilidad aprobadas.

**Flujo principal:**

1. El usuario selecciona un cliente existente.
2. El usuario selecciona un gestor comercial existente.
3. El usuario incorpora una o más piezas.
4. El usuario registra el precio acordado de cada detalle.
5. El sistema valida campos, referencias y reglas de negocio.
6. El sistema calcula o registra el total, según la decisión DD-07.
7. El sistema registra `VENTA` y sus filas de `DETALLE_VENTA` en una única
   transacción.
8. El sistema confirma el resultado.

**Flujos alternativos:**

- cliente inexistente o inactivo;
- trabajador inexistente;
- pieza inexistente;
- pieza no disponible de acuerdo con DD-01;
- detalle sin precio válido;
- intento de venta sin detalles;
- error de FK;
- fallo al insertar la cabecera o un detalle.

**Postcondiciones:**

- la venta y todos sus detalles quedan registrados, o
- se ejecuta rollback y no queda una venta parcial.

---

### CU-03. Crear un registro maestro

**Actor principal:** Usuario con permiso de mantenimiento.

**Flujo general:**

1. El usuario selecciona una de las tablas elegidas para el CRUD.
2. El sistema presenta los campos aplicables.
3. El usuario ingresa los valores.
4. El sistema valida obligatoriedad, formato, unicidad y referencias.
5. El sistema inserta el registro.
6. El sistema informa el resultado.

> Pendiente: tablas seleccionadas y campos editables.

---

### CU-04. Consultar registros maestros

**Actor principal:** Usuario con permiso de mantenimiento o consulta.

**Flujo general:**

1. El usuario abre la página de mantenimiento.
2. El sistema consulta la tabla real de MySQL.
3. El sistema muestra los registros.
4. El usuario puede aplicar los filtros implementados.

---

### CU-05. Modificar un registro maestro

**Actor principal:** Usuario con permiso de mantenimiento.

**Flujo general:**

1. El usuario selecciona un registro existente.
2. El sistema presenta sus valores.
3. El usuario modifica campos permitidos.
4. El sistema valida el cambio.
5. El sistema actualiza el registro mediante una consulta parametrizada.
6. El sistema informa el resultado.

---

### CU-06. Eliminar o desactivar un registro maestro

**Actor principal:** Usuario con permiso de mantenimiento.

**Flujo general:**

1. El usuario selecciona un registro.
2. El sistema comprueba si existen referencias.
3. Si la eliminación física no vulnera integridad y la política aprobada la
   permite, el sistema elimina el registro.
4. Si la eliminación vulnera integridad, el sistema aplica desactivación
   lógica.
5. El sistema informa claramente el resultado.

> Pendiente: política definitiva de eliminación o desactivación.

---

### CU-07. Consultar dashboard

**Actor principal:** Usuario con permiso de consulta.

**Flujo principal:**

1. El usuario abre el dashboard.
2. El sistema presenta las cuatro preguntas de negocio.
3. El usuario selecciona los filtros disponibles.
4. El sistema ejecuta consultas contra la misma base del proyecto.
5. El sistema prepara los resultados con Pandas.
6. El sistema presenta visualizaciones con Plotly.
7. El sistema muestra información suficiente para interpretar el resultado.

> Pendiente: cuarta pregunta, su consulta, visualización y filtros.

---

### CU-08. Cerrar sesión

**Actor principal:** Usuario autenticado.

**Postcondición:** se elimina o invalida la sesión activa y el sistema vuelve a
la pantalla de acceso.

# 4. Reglas de negocio

## 4.1 Reglas aceptadas como base de trabajo

Las siguientes reglas están documentadas en el informe de Fase 1. Deben
mantenerse como base provisional, excepto donde se indique que requieren una
decisión pendiente.

| ID | Regla |
|---|---|
| RN-01 | Una colección puede contener cero o muchas piezas. Cada pieza pertenece obligatoriamente a una única colección. |
| RN-02 | Toda pieza posee un código único y registra, como mínimo, nombre comercial, procedencia geográfica, fecha de adquisición, valor estimado, estado de conservación y nivel de rareza. |
| RN-03 | Una pieza puede permanecer sin clasificar. Si se mantiene la propuesta de Fase 1, una pieza clasificada pertenece exclusivamente a MINERAL, FOSIL o GEMA. La disyunción sigue pendiente de confirmación. |
| RN-04 | Una pieza puede participar en múltiples exposiciones y una exposición puede incluir múltiples piezas. |
| RN-05 | Cada participación en una exposición pertenece a exactamente una pieza y una exposición. |
| RN-06 | Un cliente puede reservar cero o muchas piezas. Cada reserva pertenece a un cliente y una pieza. |
| RN-07 | Un cliente puede tener cero o muchas ventas. Cada venta pertenece obligatoriamente a un cliente. |
| RN-08 | Cada venta es gestionada por un único trabajador. Un trabajador puede gestionar múltiples ventas. |
| RN-09 | Una venta contiene uno o más detalles de venta. |
| RN-10 | Cada detalle pertenece a una venta y se identifica dentro de ella mediante un número correlativo. |
| RN-11 | Cada detalle de venta corresponde a una pieza. La posibilidad de vender la misma pieza más de una vez está pendiente. |
| RN-12 | Una venta puede generar cero o varias evaluaciones según la propuesta de Fase 1. La multiplicidad debe ser confirmada antes de congelar el modelo. |
| RN-13 | Cada evaluación pertenece a una venta y se identifica mediante un correlativo interno a esa venta. |
| RN-14 | Un trabajador puede tener cero o una cuenta. Cada cuenta pertenece a un único trabajador, según la estructura propuesta en Fase 1. |
| RN-15 | Una cuenta puede poseer uno o más roles y un rol puede asignarse a varias cuentas, según la estructura propuesta en Fase 1. |
| RN-16 | Si se mantiene la relación de supervisión, un trabajador puede supervisar a varios trabajadores y un trabajador puede tener como máximo un supervisor directo. |
| RN-17 | Una venta debe registrarse de forma atómica: cabecera y detalles se confirman juntos o se revierten juntos. |
| RN-18 | Las operaciones deben respetar PK, FK, `UNIQUE`, `NOT NULL`, `CHECK` y demás restricciones del modelo definitivo. |
| RN-19 | Si una eliminación física vulnera la integridad referencial, debe utilizarse desactivación lógica. |
| RN-20 | Los permisos asociados a los roles deben controlar funcionalidades reales del PMV. No basta con mostrar nombres de roles. |

# 5. Entidades, atributos, PK, FK y relaciones

El siguiente esquema corresponde al modelo relacional propuesto en Fase 1. No
debe considerarse congelado mientras las decisiones DD-01 a DD-09 y DD-16
permanezcan pendientes.

Los tipos de datos, longitudes, `NULL`/`NOT NULL`, valores predeterminados,

en el modelo de MySQL Workbench antes de generar el DDL definitivo.

| `VENTA-DETALLE_VENTA` | 1:N identificadora | PK compuesta en `DETALLE_VENTA` |
| `PIEZA-DETALLE_VENTA` | 1:N preliminar | FK en `DETALLE_VENTA`; revisar DD-01 |
| `VENTA-EVALUACION` | 1:N identificadora preliminar | PK compuesta en `EVALUACION`; revisar DD-09 |
| `TRABAJADOR-CUENTA_USUARIO` | 1:0..1 preliminar | FK `UNIQUE` en `CUENTA_USUARIO` |
| `CUENTA_USUARIO-ROL` | N:M preliminar | `USUARIO_ROL` |
| `TRABAJADOR-TRABAJADOR` | 1:N unaria propuesta | FK autorreferente; revisar DD-05 |
| `PIEZA-PIEZA_CERTIFICACION` | 1:N propuesta | Revisar DD-04 |

## 5.4 Restricciones mínimas

El modelo definitivo debe declarar y justificar:

- PK de todas las tablas;
- FK de todas las relaciones;
- `NOT NULL` en atributos obligatorios;
- `UNIQUE` en los códigos naturales que deban ser irrepetibles;
- `CHECK` para dominios que se encuentren formalmente definidos;
- tipos y longitudes compatibles entre PK y FK;
- reglas de actualización y eliminación;
- índices necesarios para FK y consultas principales;
- prevención de detalles de venta sin cabecera;
- prevención de evaluaciones sin venta;
- validación de al menos un detalle por venta mediante la operación
  transaccional;
- consistencia de fechas;
- consistencia de valores monetarios;
- consistencia de la especialización, una vez aprobada DD-02.

No se debe implementar un `CHECK`, `UNIQUE` o regla de eliminación basado en una
decisión que permanezca pendiente.

## 6.3 Condiciones de implementación SQL

Cada objeto debe:

1. utilizar el modelo definitivo;
2. evitar productos cartesianos accidentales;
3. definir claramente el nivel de agrupación;
4. evitar duplicar montos por efecto de los `JOIN`;
5. tratar explícitamente valores nulos;
6. utilizar parámetros `IN` útiles en los procedimientos;
7. devolver columnas con nombres comprensibles;
8. producir resultados verificables con el conjunto de pruebas;
9. estar contenido en el script integral;
10. ejecutarse correctamente en MySQL 8.x.

## 6.4 Evidencia requerida por objeto

Para R1-R12 se debe conservar:

1. requisito redactado;
2. código completo de creación;
3. sentencia de consulta o ejecución;
4. salida real en MySQL Workbench;
5. interpretación de dos a cuatro líneas;
6. datos de prueba que permitan verificar manualmente el resultado.

### Alcance obligatorio

- seleccionar un cliente existente;
- seleccionar un gestor comercial existente;

ejemplos expresos del enunciado, pero no se consideran adoptadas hasta que el
equipo cierre DD-10.

- funcionalidades permitidas;
